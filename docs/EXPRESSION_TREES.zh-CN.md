# Expression Trees 与 XSIMPKIT 的适配评估

结论：可以参考它组织自定义改写规则的方式，但不宜把原库直接接入当前化简管线，也没有证据表明换用它会让 XSIMP 更快。当前 XSIMP 已经直接遍历 CAS 的带类型表达式树；这个库额外把整棵树复制成嵌套列表，再递归重建。

## 实际源码做了什么

来源：[hpcalc.org 项目页](https://www.hpcalc.org/details/9644)及其[原始下载包](https://www.hpcalc.org/prime/math/trees.zip)。作者为 Nikolaus Henderson（ftneek），文件日期为 2024-08-16。

下载包只有 `trees.hpprgm` 与 `trees.html`。检查了原生程序内的完整 CAS 源码：

- `build_tree` 把符号节点转换为“运算符、子树列表”；数字、变量、列表及矩阵整体作为叶子。它使用递归和 `append` 构造列表。
- `build_expr` 递归重建参数后调用原运算符 `f(l)`，因此会执行原生求值。包内作者说明也明确承认重建时总会求值，尚未解决阻止求值的方法。
- `sgamma` 演示 Gamma 函数规则，最后仍调用原生 `simplify`。它不是新的通用 CAS 算法，也没有附带提速测试。

## 兼容性实测

在独立 HOST Giac WASM 的 HP 模式中加载原程序，只去掉文件容器的 `#cas` / `#end` 包装，没有修改函数实现。设置为 `calc_mode(-38)`、一基索引和弧度。结果不能代替 HP Prime G2 实机测试。

| 调用 | 实际结果 | 对当前项目的意义 |
| --- | --- | --- |
| `build_tree(quote(x^2))` | `['^',[[x],[2]]]` | 基础建树可用 |
| `build_expr(build_tree(quote(c/c)))` | `1` | 重建约掉了原来的分母限制 |
| `build_expr(build_tree(quote(sqrt(4-2*i))))` | `2.05817102727-0.485868271757*i` | 重建把受保护的精确复根变成近似数 |
| `build_tree(quote([[x,1],[i,0]]))` | `[[[x,1],[i,0]]]` | 矩阵作为一个叶子，不会逐元素套用规则 |

这与 XSIMP 所要求的“保留精确数、保留受保护结构和新增规则的分母限制”直接相关。直接替换现有树操作会重新引入这些已知风险。

## 对效率的判断

做了一个只测基础设施的 HOST 微基准。对照函数只读取原生树并统计节点，原库函数则建立完整列表树；两者工作量不同，不能把差值解释为整个 XSIMP 的加速或减速比例。

| 输入 | 遍历节点数 | 原生树计数中位耗时 | 原库建列表树中位耗时 |
| --- | ---: | ---: | ---: |
| 简单虚数指数配对 | 15 | 0.187 ms | 0.234 ms |
| 项目原有长表达式样例 | 650 | 7.909 ms | 9.525 ms |
| 40 项宽多项式 | 201 | 1.971 ms | 3.459 ms |

每项先预热两次，再测九轮，每轮三次调用；没有随机交错、专门控制垃圾回收或模拟实机频率。这是 1.8.4 阶段的历史基础设施测量，原始记录路径为 `validation/integration184/expression-tree/benchmark.json`；它不属于 1.8.5 的完整化简性能证据。测量只说明列表树转换本身有成本，尚未评估一次建树后复用许多规则是否能摊销该成本，也未测原生模拟器或 G2 上的整个 XSIMP。

更值得尝试的方向是：在已有的带类型原生树上合并相容的后序遍历、缓存一次调用内重复使用的节点属性、减少字符串往返和昂贵 CAS 调用。每项改动都应使用相同输入、相同输出及相同精确性/定义域要求做性能对比，再决定采用。

本次整合无需引入这个第三方运行库。原包未附独立许可文件或明确再分发声明，项目中只保留本评估与测量记录，没有把原库源码复制进 XSIMPKIT。
